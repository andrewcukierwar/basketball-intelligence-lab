# Evaluation run manifest

**Status:** Proposed schema v1 for [issue #4][issue]. **Classification:** Original BIL design. The [validation strategy](validation-strategy.md) specifies allowed data, splits and claims. The [canonical data contract](data-contracts.md#provenance-and-time) specifies record availability and revision selection.

## Immutable stages

A **forecast manifest** records the committed model, data views, fitted artifacts and forecast bytes for each origin. A **score manifest** links the forecast manifest by run ID and SHA-256 and uses a separately frozen label view. It can be rebuilt for revised truth or metrics under a new run ID, preserving all earlier results and the prediction bytes. Score-stage inputs cannot enter forecast lineage. Distinguish primary scoring, realized-lineup or oracle diagnostics, and permitted external EPM agreement in score manifests.

Freeze the protocol registration and candidate configuration before accessing holdout outcomes for evaluation or design. A registration is a dated, content-addressed record containing the exact split boundaries, frozen code and configuration, update and training policy, target cohorts, metrics, baseline definitions, selection policy and uncertainty method. A retrospective holdout registration can postdate the games. A prospective registration must precede its first declared origin and specify the schedule of expected origins. Preserve the time, scope and purpose of holdout accesses. An append-only timestamp receipt for each prospective batch attests its origin, registration, deadline, cohort with statuses and prediction bytes. A later manifest can index those receipts.

Store manifest JSON as an immutable artifact, and hash exact file bytes with SHA-256. Hashes cover effective configuration, input selection, fit artifacts and forecast bytes. The Git revision pins code. For reproducible research runs, the checkout must be clean. For deterministic steps record that policy; for random steps record seeds and execution constraints. A repeat is a new run with a new ID and references to the original. Keep failed or invalidated attempts in the [experiment log](experiment-log.md).

## Common fields

Types use `id` for nonempty strings, `sha256` for a 64-character lowercase hex digest, `instant` for UTC ISO timestamps, and `date` for ISO Eastern played dates. `i32` and `i64` are integers, `f64` is a finite numeric value, `T[]` is an array, and a trailing `?` marks a nullable field. Declared paths can address local or private artifact storage. Tokens and restricted rows stay outside the manifest and Git.

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version`, `run_id`, `experiment_id` | `i32`, `id`, `id` | Version the manifest schema and identify this immutable execution and its experiment-log entry. |
| `stage`, `evaluation_mode`, `created_at` | `enum{forecast,score}`, `enum{retrospective,strict_rolling,prospective}`, `instant` | Stage and claim. Creation time is when the manifest was written. Origin and freeze times have distinct fields. |
| `status`, `reason`, `parent_run_id` | `enum{completed,failed,invalidated}`, `text?`, `id?` | Retain attempts and reasons. A retry or invalidation record identifies its predecessor. A score run links the forecast separately below. |
| `code_git_sha`, `environment_artifact_id` | `id`, `id` | Full code commit and environment record, including dependency lock digest, Python, execution platform and relevant library or execution settings. The environment record describes software used. |
| `config_artifact_id`, `seeds`, `registration_artifact_id` | `id`, `seed_record[]`, `id` | Effective configuration (features, model, baselines, fitting and prediction choices), explicit seeds by component, and immutable registration artifact. A seed record has `scope: id` and `seed: i64`; use an empty list for a deterministic procedure. |
| `protocol_id`, `registered_at`, `splits` | `id`, `instant`, `split[]` | Evaluation protocol version, timestamp evidenced by the registration artifact, and populated split definitions. See below. |
| `artifacts`, `input_views` | `artifact[]`, `input_view[]` | Dated inputs and outputs with content hashes, and exact selections of canonical records. |
| `forecast`, `score` | `forecast_payload?`, `score_payload?` | A completed run has exactly the payload for its stage. A failed run can retain available partial artifacts with reason and stage. Invalidation references the affected run without rewriting it. |

| Record | Required fields and semantics |
| --- | --- |
| `split` | `split_id: id`, `role: enum{fit,validation,holdout,prospective}`, `start_date: date`, `end_date: date` (exclusive), `season_start_years: i32[]`, `season_types: id[]`. Record the exact cohort/target recipe and fit update policy in the registration. Target windows or horizons cannot straddle splits. Inner validation folds can subdivide the initial fitting range under the registered protocol. |
| `artifact` | `artifact_id: id`, `kind: enum{registration,config,environment,source,selection,cohort,fitted_state,predictions,freeze_receipt,forecast_manifest,metrics,access_log}`, `uri: text`, `sha256: sha256`, `size_bytes: i64`, `source_artifact_id: id?`, `rights_ref: id?`. Source records additionally require canonical provenance and a rights reference. Record which source IDs and roles feed each selection. Restricted artifact references can resolve privately. |
| `input_view` | `view_id: id`, `role: enum{features,fit,outcomes,external_epm}`, `as_of_at: instant`, `selection_artifact_id: id`, `source_artifact_ids: id[]`, `max_known_available_at: instant?`, `unknown_availability_count: i64`, `selected_count: i64`, `exclusions: count_by_reason[]`. Selection artifact enumerates canonical keys and revisions, source/evidence pointers, chosen and rejected inputs and applicable observed dates/outcome horizons. For a forward fit view it includes per-example feature origins, parent prediction fit IDs where applicable, and label close and availability evidence. Include all preprocessing dependencies. Strict input views require zero selected rows with unknown availability. The summary fields support audit without replacing row-level eligibility proof. |

A `count_by_reason` record is `{reason: id, count: i64}`. Counts and bytes are nonnegative. A local artifact ID is unique within its manifest. References resolve to artifacts or views in that manifest, except for explicitly named linked runs or canonical source IDs. The registration and selection file formats may evolve independently with pinned digests.

## Forecast payload

- **`fits: fit[]`.** Each record has `fit_id: id`, `component: id`, `fit_as_of_at: instant`, `generated_at: instant`, `fit_view_id: id`, `config_artifact_id: id`, `state_artifact_id: id`, and `parent_fit_ids: id[]`. Record every learned dependency, including independent RAPM target generation, SPM, preprocessing, skills, minutes, fit-derived baselines and calibration. Fit links form an acyclic dependency graph. A parent fit's cutoff and actual generation time cannot exceed the child's respective values. Each fit view cutoff equals the referenced fit cutoff. For every forecast, all reachable fits must respect its origin cutoff and must have existed by prediction generation.
- **`batches: forecast_batch[]`.** Each batch has `batch_id: id`, `split_id: id`, `origin_at: instant`, `rating_date: date?`, `feature_view_id: id?`, `fit_ids: id[]`, `target_artifact_id: id?`, `predictions_artifact_id: id?`, `generated_at: instant?`, `deadline_at: instant?`, `frozen_at: instant?`, `freeze_receipt_artifact_id: id?`, `status: enum{generated,missing}`, and `missing_reason: id?`. For generated predictions, require the feature view and target artifact and set the view cutoff to the batch origin. Cohort and prediction files use a stable target key such as `(game_id, player_id, stat_code)` or `(game_id, target_code)`. The cohort file lists every expected key and its prediction or missing status at freeze. Generated batches require the prediction digest and execution time. Prospective scoring verifies timing against actual tip per target. Missing batches preserve the expected keys when evidenced, and otherwise retain the expected origin and missing-coverage reason.

For forward calibration and stacking, the selection artifact identifies each training row's feature origin and the exact parent prediction fit IDs for that row. Each referenced fit has a cutoff at or before the row's origin and a valid transitive lineage. The fit graph records the union of dependencies. A parent that passes the child cutoff test can still fail the row cutoff test. A historical SPM estimator uses the declared same-window calibration rules in the [validation contract](validation-strategy.md#origins-fitting-and-outcome-isolation).

The timestamped prospective freeze receipt binds `registration_sha256: sha256`, `origin_at: instant`, `deadline_at: instant`, `cohort_sha256: sha256`, `predictions_sha256: sha256?`, and `frozen_at: instant` to independent evidence named by `timestamp_evidence_ref: id`. Score a generated target as prospective only when its receipt, digests and timing verify. A receipt can attest a cohort with all predictions missing. Verify the origin and registration against the manifest. The scoring coverage report reconciles every registered origin, including missing receipts. Independently timestamped origin inputs can supply an expected cohort for a missed batch. Where no such cohort can be established, report the missing origin and incomplete coverage denominator.

Only the source roles allowed for fitting and prediction appear in either selection lineage. Disallow external EPM values, target outcomes, realized target-game exposure and final target-game lineup data in pregame inputs. A strict replay executed later may have an actual `generated_at` after the historical origin or tip. It has no prospective freeze claim.

## Score payload

- **References.** Record `forecast_run_id: id`, `forecast_manifest_artifact_id: id`, `outcome_view_id: id`, `scoring_as_of_at: instant`, `score_kind: enum{independent_basketball,realized_lineup_diagnostic,oracle_minutes_diagnostic,external_epm,synthetic}`, `access_log_artifact_id: id`, and `metrics_artifact_id: id`. The forecast manifest artifact points to the bytes with verified hash. It pins predictions by digest, so scoring cannot substitute another model or forecast. The outcome view cutoff equals the scoring cutoff. Use a separate outcome view and score run for external EPM values.
- **`results: metric_result[]`.** Each result has `split_id: id`, `cohort_id: id`, `metric_code: id`, `unit: text`, `model_id: id`, `baseline_id: id?`, `value: f64?`, `paired_delta: f64?`, `interval: f64[]?` (lower and upper bounds), `games_scored: i64`, `targets_expected: i64?`, `targets_scored: i64`, `sum_weights: f64?`, and `exclusions: count_by_reason[]`. Paired delta is the candidate metric minus the baseline metric on identical targets. Record paired and full cohorts, dependencies, confidence and weighting definitions in the registration and metrics file. Use null with an explanation for unavailable scores or unknown target denominators. For prospective runs, include a timing/coverage report by origin and target. Record holdout and external benchmark access separately, including when the results were exposed to analysts.

## Local historical checks

From an installed development checkout, validate the synthetic replay and recompute its linked score.

```sh
uv run --locked python -m bil.evaluation \
  tests/fixtures/evaluation/synthetic_forecast.json \
  --score tests/fixtures/evaluation/synthetic_score.json
```

Omit `--score` to check a forecast stage by itself. The command reads local artifacts without changing them. It checks completed retrospective and strict rolling-origin manifests and recomputes unweighted scalar `margin_mae`, `margin_rmse` and `possession_mse` on frozen targets. Score a later outcome revision in a separate run linked to the same forecast. Wholly missing batches require an evidenced target roster to produce a complete checked denominator. Daily forecasts only match outcomes played on the frozen rating date. The target roster is supplied by the run, and its reconstruction from dated schedule evidence belongs to the forecast producer. The command supports one scored origin per target key and leaves prospective receipt verification and richer protocol-specific scoring to later implementations.

The [forecast fixture](../tests/fixtures/evaluation/synthetic_forecast.json) illustrates a historical origin with two learned dependencies. The [score fixture](../tests/fixtures/evaluation/synthetic_score.json) pins its exact bytes and independently selects a mature outcome. The companion [synthetic artifacts](../tests/fixtures/evaluation/synthetic/) provide the checked selection proofs, target roster, predictions and metric results. Source, fit-state, config, environment, registration and access-log entries in these examples are fabricated metadata. The command checks their references, including the fitted-state and config entries. It verifies the bytes it consumes, including all local selection, cohort, prediction and metrics files. Source publication evidence and selected dependencies need upstream provenance before any real historical claim. No NBA data or actual forecasts are present in the fixtures.

### Local row-level evidence format

- Each selection JSON object contains `revisions` and `selected`. A candidate revision has `key`, `revision`, `source_artifact_id`, `content_sha256`, `kind`, `availability_basis`, `available_at` and `evidence_ref`. A source must appear in the view. Use `schedule`, `observation`, `outcome` or `external_epm` for `kind`. Include `observed_date`, `observed_at` or `finalized_at` as applicable and set `change` on retractions. For a supervised outcome, `finalized_at` is when its entire horizon closed. This proof records horizon closure. Establishing each example’s horizon start requires separate evidence. `selected` lists the chosen `[key, revision]` pairs in key order. Historical replay may select an unknown or later-published revision, with visibility limits explicit in the pinned proof and view summary.
- A fit selection declares `training_mode`. A `historical_estimator` records its half-open `calibration_window` as two dates. A `forward` fit records `training_examples`, each with a `label` pair, `origin_at`, optional `rating_date`, feature revision pairs in `features` and the `parent_fit_ids` that predicted that example. Its `prediction_parent_fit_ids` names which graph parents supply those row-level predictions. Revisions include earlier feature versions needed to check each example against its own origin.
- A cohort JSON object contains `targets` with stable `key`, `game_id`, `season_start_year`, `season_type`, `cohort_id` and `status`. Predictions contain the generated keys and a nonempty `values` mapping from model ID to finite numeric prediction for each key. An outcome selection adds `outcomes`, each with the selected `key` and `revision`, matching game and season identifiers, `value` and the observed `actual_tip_at` where evidenced. The `metrics` file records the manifest's `results` array.

Feature and fit builders should resolve revisions before caching their inputs. The selected immutable revision records, including their content hashes, distinguish visible corrections without incorporating rejected future rows. Include the applicable code, specification and model configuration in derived cache identity.
